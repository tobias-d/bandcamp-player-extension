Building a Browser-Based DJ Audio Engine

How a Bandcamp player extension plays music, changes its tempo without changing its pitch, scrubs instantly, and switches tracks without a gap — and every audio idea you need to understand to build something like it yourself.

Introduction

This guide explains the complete audio system of a browser extension that turns Bandcamp into a DJ-style player. It is written for someone who has never touched audio programming. We start from "what is a sound wave in a computer" and build all the way up to gapless track switching and pitch-preserving tempo control.

The player does four things that sound simple but are surprisingly deep:

  • Plays a track — but through its own audio engine, not just the web page's <audio> tag.
  • Changes tempo (speed) without changing pitch — a 174 BPM track at 140 BPM that still sounds in-key. This is time-stretching.
  • Seeks instantly — drag the waveform and audio jumps there with no rebuffering.
  • Switches tracks with no gap or click — the way a DJ deck does.

Each of these forces a design decision, and those decisions stack into a real architecture. We will follow the why behind every layer. Code references point at the real files so you can read along; snippets are simplified for clarity but faithful to the actual design.

How to read this

Parts 1–3 are pure foundations (sound, Web Audio, the extension sandbox). Parts 4–7 are the architecture. Parts 8–12 are the features and the genuinely hard problems. Part 13 distills the engineering lessons. If you already know Web Audio, jump to §4.

1 · How digital sound works

Sound is a wave — air pressure rising and falling. A microphone measures that pressure many thousands of times per second. Each measurement is a number. That stream of numbers is the digital sound.

Sample rate

The number of measurements per second is the sample rate. CD-quality and most web audio is 44,100 samples per second (44.1 kHz). Each measurement is a sample. So one second of audio is 44,100 numbers; a 6-minute track is about 16 million of them.

Channels (stereo)

Stereo means two independent streams — left and right. So a stereo track is two arrays of 44,100 numbers/second. In code we hold each as a Float32Array (an array of decimal numbers between −1.0 and +1.0, where 0 is silence and ±1.0 is the loudest the format allows).

Key number

A 4-minute stereo track decoded to raw samples is roughly 4 min × 60 × 44,100 × 2 channels × 4 bytes ≈ 84 MB. Compressed (MP3) it was ~5 MB. Decoded audio is ~15× bigger than the file you downloaded. Remember this — it drives half the architecture later (memory limits, why we don't copy buffers carelessly).

PCM vs. compressed

An MP3 file is compressed — clever math throws away data your ears barely notice. To actually play it, the computer must decode it back into raw samples, called PCM (Pulse-Code Modulation). PCM is the universal "raw" form every audio engine works with.

Buffers, the audio thread, and underruns — the most important idea here

Your speakers need a perfectly steady stream of samples. If even a few thousand samples arrive late, you hear a click, pop, or crackle. To guarantee steadiness, the operating system runs a dedicated real-time audio thread that asks your program, over and over, "give me the next ~128 samples, right now." This little chunk is a render quantum or audio buffer.

The crackle rule

The audio thread runs on a deadline of a few milliseconds. If your code can't produce the next buffer of samples in time — because the main thread is busy, or memory is being copied, or the CPU is overloaded — the audio thread gets silence instead of sound. That gap is an underrun (a.k.a. buffer underflow / "glitch" / "xrun"). Underruns are the root cause of almost every crackle in this entire project. Keep this in mind for §11.

Latency

It takes time for a sample to travel from your code, through buffers, the OS mixer, and out the speaker. That delay is output latency — often 5–20 ms. It feels instant, but when you're trying to align two audio sources or fade one out exactly as another starts, those milliseconds matter enormously.

2 · The Web Audio API

Browsers give JavaScript a real audio engine called the Web Audio API. You don't push samples to the speaker yourself; instead you build a graph of nodes, and the browser's audio thread pulls audio through it.

AudioContext

Everything lives inside an AudioContext — the engine. It has a sampleRate, a master clock (currentTime, in seconds, that only ever moves forward), and a destination (your speakers). You schedule things against currentTime: "start this at currentTime + 0.1."

const ctx = new AudioContext({ sampleRate: 44100 });
const gain = ctx.createGain();      // a volume knob node
gain.connect(ctx.destination);    // wire it to the speakers
gain.gain.value = 0.8;             // 80% volume

Nodes and the graph

Audio flows from source nodes, through processing nodes, to the destination. A few you'll meet here:

NodeWhat it does
GainNodeMultiplies the signal by a number. Volume control, and — crucially — smooth fades (ramp the gain from 0→1 over 8 ms to avoid clicks).
AnalyserNodeLets you read the signal's current level/spectrum without changing it. Used for meters and debugging.
ConstantSourceNodeOutputs a steady value. Here it's a trick to keep the context "awake" (more in §6).
AudioWorkletNodeThe big one: your own audio code running on the real-time audio thread.

decodeAudioData — turning a file into samples

To get PCM from a downloaded MP3, you hand the compressed bytes to the context:

const bytes = await (await fetch(url)).arrayBuffer();
const audioBuffer = await ctx.decodeAudioData(bytes);
// audioBuffer.getChannelData(0) -> Float32Array of the left channel

The result is an AudioBuffer: the decoded PCM, ready to play. Decoding happens off the main thread, but the result is a big chunk of memory (remember: ~84 MB for a 4-minute track).

AudioWorklet — your code on the audio thread

An AudioWorklet is a small JavaScript/WebAssembly program that the audio thread calls for every render quantum. It runs in a separate, real-time context with one job: fill the next buffer of samples, on time, every time. This is where our time-stretching engine lives. Because it runs on the audio thread, it must never be slow and never allocate memory carelessly — or you get underruns (crackle).

Why a worklet at all?

The browser can play an AudioBuffer at normal speed by itself. But to change speed without changing pitch, we need custom DSP (digital signal processing) math running sample-by-sample. That custom math is the worklet. We use an off-the-shelf one called SignalSmith Stretch.

3 · The browser-extension trap

If this were a normal website we could stop at §2. But it's a browser extension that injects itself into bandcamp.com, and that creates three hard constraints that shape the whole design.

Constraint 1 — There's already an audio player on the page

Bandcamp has its own <audio> element playing music. We don't control how it started. So at any moment, sound might be coming from Bandcamp's player (we call this origin audio) or from our engine (runtime audio). Two players, one pair of speakers. Managing who is in charge is the single most error-prone part of the system (see §5).

Constraint 2 — Content Security Policy blocks WebAssembly

Bandcamp's page sets a Content Security Policy (CSP) — a security rule that, among other things, blocks WebAssembly from loading in code injected into their page. Our time-stretch worklet is WebAssembly. So it literally cannot run in the page's context.

The clever escape

Extension's own pages are not subject to Bandcamp's CSP. So we create a hidden <iframe> pointing at an moz-extension://…/runtime-audio-host.html page that we own. Inside that iframe, WebAssembly and AudioWorklet load normally. All real audio playback happens inside this iframe. The page's content script talks to it by sending messages. This indirection is the backbone of the architecture. runtime-audio-host.ts runs inside the iframe; host-player.ts is the page-side remote control.

Constraint 3 — Three separate worlds, joined only by messages

A browser extension is split across isolated contexts that cannot share variables — they can only pass copyable messages:

ContextRuns whereJob
Content scriptInside the Bandcamp pageThe brain: UI, decides who owns playback, fetches audio, coordinates everything.
Background / workerThe extension's own processHeavy lifting that shouldn't block the page: BPM analysis, waveform extraction (WebAssembly number-crunching).
Host iframeHidden extension pageThe actual audio engine: AudioContext + SignalSmith worklet → speakers.

Because they only exchange messages, every command ("load this track", "seek to 2:54") is an async round-trip with a confirmation message (an ACK). That asynchrony — and the races it creates — is a recurring theme.

5 · The ownership model

This is the heart of correctness. Because there are two possible sound sources (Bandcamp's element and our engine), the system must always have exactly one authoritative owner of playback. Ambiguity here is the source of double-audio, silent players, and crackle.

Three states

The controller tracks an explicit ownership state (controller.ts, RuntimeAudioOwnershipState):

StateMeaning
origin-startedBandcamp's own <audio> is the audible source. This is how playback naturally begins.
runtime-pendingThe user picked a track through our UI, but its audio isn't decoded/ready yet. We've paused the old owner and are waiting. The UI shows a loading shimmer.
runtimeOur iframe engine is the audible source. Tempo, key lock, and seeking all live here.

The golden rules

These rules (from the project's runtime-audio.md) exist because every time they were fudged, a bug appeared:

  1. Ownership is decided by who started the track. The first Bandcamp-origin track is origin-owned. Anything the user selects through our playlist is runtime-owned.
  2. Origin → runtime handover happens only on an explicit action: a seek or a tempo change. Background work (like pre-decoding the next track) must never silently switch the owner.
  3. "Prepared" is not "owned." Having a track's PCM decoded and ready does not mean we're playing it. These are different facts and the debugger shows both.
  4. One transition owns the moment. While a handover runs, stray events (e.g. a late notification from Bandcamp's element) must not start a competing transition.
Why "neutral tempo" still uses our engine

You might think: if the user didn't change the tempo (rate = 1.0), why not just let Bandcamp's element play? Because then the next action (a seek, a tempo nudge) would force a mid-playback handover — and handovers are exactly where crackle happens. Keeping selected tracks in our engine from the start means later controls are smooth. Consistency beats cleverness.

A handover, step by step

When an origin-owned track gets its first seek, handoverToRuntime() runs roughly:

  1. Fade origin out first (origin-muted-before-runtime-work) — silence Bandcamp's element before doing any engine work, so the listener never hears the seam. Crucially this is a short fade (~20 ms ramp to zero), not an instant volume = 0: stepping the volume straight to zero mid-waveform is itself a discontinuity → a click (the same kind §11 fades on the engine side). Mute only after the ramp reaches zero.
  2. Load the decoded PCM into the iframe engine and schedule playback behind a handoff gate (a hard mute on the engine's first output — see §11).
  3. Wait for the engine to confirm it's producing sound (runtime-ready-before-origin-pause).
  4. Then pause Bandcamp's element and mark ownership transferred.

The ordering — mute, prepare, confirm, then pause — guarantees there's never a silent gap nor an audible overlap.

6 · The runtime host & its audio graph

Now we open the iframe. runtime-audio-host.ts builds a fixed chain of Web Audio nodes. Every sample we play flows through it:

Why each node exists

  • stretchNode — the SignalSmith AudioWorklet. PCM goes in; tempo-/pitch-adjusted samples come out. This is the only "smart" node.
  • handoffGate — a GainNode used purely to hard-mute the engine's very first output window, then fade it in. The worklet's first few milliseconds after a cold start can contain garbage/transients; muting them is the main anti-crackle trick (§11).
  • gain — user volume, multiplied by a fixed 0.78 headroom factor. Real Firefox traces showed the stretched signal peaking above 1.0 right after a start, which clips (distorts); the headroom prevents that.
  • analyser — reads the output level so the code can prove sound is actually playing (used in diagnostics and the "first window" probe).

Match the context to the track

The AudioContext is created at the decoded track's sample rate (usually 44,100 Hz). If the context ran at a different rate, the browser would resample on the fly — extra work and a quality/latency cost. Matching rates means the worklet feeds samples through 1:1.

The keep-alive trick

Firefox throttles or suspends audio in hidden/inactive documents. Two defenses: (1) the iframe is positioned as a 1×1px, invisible-but-on-screen element so Firefox doesn't treat it as inactive; (2) a silent ConstantSourceNode stays connected to keep the context "running." Without these, audio would stutter whenever the tab wasn't focused.

The command protocol

The page (host-player.ts) and the iframe (runtime-audio-host.ts) speak a tiny message protocol. Commands carry an ackId; the iframe replies with a matching ACK so the page knows when work truly finished:

// page → iframe
{ type:'LOAD_TRACK', ackId, url, channels: Float32Array[], sampleRate, numberOfFrames }
{ type:'PLAY_FROM_TIME', ackId, positionSec, playbackRate, keyLockEnabled, handoffGate }
{ type:'SEEK_TO_TIME', positionSec }
{ type:'STOP', ackId, drainOutputBeforeClear }

// iframe → page
{ type:'HOST_READY' }
{ type:'ACK', ackId, ...info }
{ type:'STATE', paused, currentTimeSec, durationSec }
{ type:'ENDED' }

Notice channels: Float32Array[] — the raw PCM is sent across the iframe boundary. How you send it matters a lot, which the pipeline section covers next.

7 · The audio pipeline, end to end

Let's follow one track from a click to sound coming out, naming the real steps.

  1. Fetch — the content script downloads the compressed audio (a Bandcamp stream URL) as an ArrayBuffer (~5 MB).
  2. Decode — decodeAudioData() turns it into an AudioBuffer of raw PCM (~84 MB). This is stored in the prepared-track cache (engine.ts).
  3. Hand PCM to the iframe — on LOAD_TRACK, the channels (Float32Arrays) are posted into the host iframe.
  4. Load into the worklet — the iframe feeds the PCM into the SignalSmith node's input buffer.
  5. Schedule — PLAY_FROM_TIME tells the worklet where to start and at what rate, behind the handoff gate.
  6. Render — the audio thread pulls samples through the graph; the gate fades in; sound plays.
Pitfall: copying 84 MB on the main thread

Sending PCM into the iframe can be done two ways. A transfer moves the memory (zero-copy, instant) but empties the original — so you can't keep it cached. A copy (.slice(0)) duplicates it so the cache survives, but copying ~84 MB on the main thread blocks everything for a noticeable beat. This project copies (because the cache must survive for instant re-seeks/ping-pong), and that copy cost is a known hotspot — exactly the kind of main-thread stall that, taken to an extreme bug, once froze the whole tab. Always know whether you're transferring or copying, and how big it is.

The prepared-track cache & memory awareness

Decoded tracks are huge, so we can't keep them all. engine.ts keeps a bounded cache and evicts the oldest when over a track-count cap or a total-bytes budget. The budget adapts to the device:

Device memory signalTracks kept (decoded budget)Concurrent decodes
unknown (Firefox usually hides it)8 (~850 MB)2
< 4 GB (only Chrome reports real RAM)6 (~440 MB)1
< 8 GB8 (~750 MB)2
≥ 8 GB10 (~1200 MB)3
Chrome Performance opt-inwindow 24 / retain 30 (~2900 MB)4
Two things to notice

(1) "Unknown" is no longer the rock-bottom floor. Firefox hides the memory hint, so it lands on the unknown row — which used to be the most conservative (~4 tracks). Once the chunked feed (§11) removed the load crack and encoded-blob retention (§12) made eviction cheap, that floor was raised to 8 tracks / ~850 MB. A genuinely low-RAM machine only drops further if it reports < 4 GB, which only Chrome does. (2) The Performance row is Chrome-only and opt-in. Chrome caps the reported memory at 8 GB, so high-RAM machines can't climb past the ≥ 8 GB tier automatically; a user setting unlocks the top tier, the only one where the look-ahead window (24) is smaller than what's retained (30) — the extra tracks stay decoded behind the playhead for instant look-back.

Subtle correctness detail

The eviction loop must always keep at least one track — a single 38-minute mix can exceed the entire byte budget by itself, and a naïve "evict until under budget" loop would try to evict the very track it's about to play, or loop forever. Boundary conditions in eviction logic are a classic source of infinite loops.

8 · Tempo & key lock — the magic trick

Play a record faster and it gets higher-pitched (chipmunk effect), because speed and pitch are physically tied together. DJs want to change tempo without pitch. Doing that digitally is time-stretching, and it's genuinely hard math.

Naïve vs. real

  • Resampling (what audio.playbackRate does): play the samples faster. Tempo ↑, pitch ↑. Wrong for DJing.
  • Time-stretching (what we want): analyze the sound into short overlapping grains and re-space them in time without moving their frequency content. Tempo changes, pitch stays. This is what SignalSmith does in the worklet.

Key lock (a.k.a. master tempo) is the mode where pitch is held constant while tempo varies — i.e. time-stretching is on. Turn it off and you get classic vinyl-style pitch-bending.

Hard rule from the project

Tempo adjust is SignalSmith-only. The browser's built-in playbackRate/preservesPitch is explicitly forbidden as a product path — even as a "fallback." If the worklet can't run, tempo controls disable themselves and say so, rather than silently switching to inferior native stretching. No silent fallbacks is a core design value here: a hidden fallback hides bugs and produces inconsistent sound.

Changing tempo while already playing

If our engine already owns the track, a tempo change is cheap: just send SET_TEMPO to the worklet (runtime-active-controls-synced). No reload, no re-decode. If origin still owns the track, the tempo change triggers a handover first (§5), then sets the rate. That's why the very first tempo nudge on a fresh track does more work than the ones after it.

9 · Seeking (scrubbing)

Dragging the waveform fires a flood of seek requests — one per animation frame, ~60 per second. Three different situations, three behaviors:

SituationWhat happens
Runtime owns itSend SEEK_TO_FRACTION to the worklet. Instant — the whole track's PCM is already in memory, so jumping is just moving a read position.
Origin owns it, track is decodedThis seek is an explicit action → hand over to runtime, seeking to the target position as part of the handover.
Origin owns it, not decoded yetRemember the target, kick off decoding, show a loading state, and apply the seek once the track is ready.

Coalescing the flood

You must not act on all 60 events/second. The code coalesces: it keeps only the latest requested position and collapses repeats. Two layers do this — the waveform UI throttles drag events to one per frame, and the controller only re-runs work when the target actually changed.

War story: the busy-loop freeze

A retry loop in the seek handover re-queued itself with no delay whenever a handover "still looked needed." If the handover kept failing for a permanent reason, it spun forever — pinning the CPU at 100% and allocating memory until the browser warned, then froze the tab (it reached tens of GB of memory). The fix: only re-run when a genuinely newer seek arrived; a repeated identical failure must stop, not spin. Lesson: any self-re-queuing async task needs a termination condition that a persistent failure will actually hit.

10 · Gapless track changes: two-host ping-pong

The hardest "simple" feature. When you switch from track A to track B, the obvious approach is: stop A, load B into the engine, start B. But loading B (sending ~84 MB of PCM and feeding the worklet) takes time on the audible engine — and that work, competing with the real-time audio thread, causes a click or gap right at the switch.

The solution: double-buffering, like graphics

Keep two complete host iframes alive at all times — call them active and idle. Each has its own AudioContext and worklet.

  1. Load B into the idle (silent) host. The costly clear + addBuffers happens off the audible path, so A never glitches.
  2. Start B on the idle host behind its handoff gate.
  3. Swap: idle becomes active. B is now audible.
  4. Retire the old active (was A): fade it out, let its already-queued output drain, then clear it. It becomes the new idle, ready for the next switch.
Why "drain" matters

When you stop a source, samples are already buffered downstream heading to the speaker. If you tear the node down instantly, those queued samples are cut off mid-wave → a click. Draining means: fade to zero, then keep the (now-silent) node alive for a little longer than the output latency, so the queued tail finishes cleanly before you destroy anything.

A debug line Runtime host pair: active=…:<trackId> idle=…:<trackId> shows the two hosts; the active id flips on every switch, which is how you confirm ping-pong is actually engaging.

The catch on Firefox

"Load B off the audible path" assumes the idle host's work is truly off the audible path. On Chrome it is — each AudioContext renders on its own thread, so loading B into the idle host can't disturb A. Firefox renders all AudioContexts on one shared audio thread. So the costly addBuffers on the idle host still competes with A's real-time render on the same thread — and ping-pong alone doesn't save you. That's the problem §11 actually solves.

11 · Crackle & the real-time thread — the deep problem

Everything above orbits one enemy: the click/pop/crackle at transitions. This section is the most important audio content in the guide, because it's where intuition fails.

What crackle actually is

Recall §1: the audio thread needs the next buffer of samples on a hard deadline. Crackle happens when either (a) it gets silence because we were late producing samples (an underrun), or (b) it gets a sudden jump in the waveform — a discontinuity — because we started, stopped, or swapped audio at a non-zero point without a fade.

The four anti-crackle tools

ToolDefends againstHow
Micro-fade (8 ms in, 20 ms out)Discontinuity clicksNever start or stop at full volume on a sample. Ramp gain 0→1 (or 1→0) over a few ms so there's no instantaneous jump.
Handoff gate (120 ms hard mute)Garbage in the worklet's first outputA freshly-started time-stretch worklet's first blocks can be unstable. Hard-mute the gate node for ~120 ms, then fade in — the listener only hears clean audio.
Preroll (30 ms)Cold worklet not "warmed up"Feed the worklet samples before the audible start point so its internal pipeline is primed when sound is supposed to begin.
Output drain (latency + 30 ms)Cut-off tails on stopKeep a faded-out node alive until the already-queued samples have left the sink (§10).
Chunked feed (~3 MB slices, Firefox)The load-transfer stall (below)Send the track's PCM into the worklet as many small slices with a yield between each, so no single transfer blocks the shared audio thread long enough to underrun.

The subtle cold-start bug

Here's a real, non-obvious case. A mid-track start can preroll 30 ms of audio (the samples just before the seek point exist). But a track change starting at 0:00 can't preroll — there is nothing before sample zero. So a fresh track at t=0 gets less worklet warm-up than a mid-track seek, and on a slow machine that shortfall is the difference between a clean start and a crackle.

The fix: when starting cold at t=0, hold the handoff gate longer by exactly the missing preroll time, so every cold start gets the same total warm-up (~150 ms) before the audible fade-in. You can see it in the debug trace as gate=150ms/30ms on track changes vs. 120ms/30ms on mid-track handovers.

Why this is so hard to debug

Two brutal realities: (1) Fast machines hide it. A developer's quick CPU produces buffers in time even when doing wasteful work; a slower machine starves the audio thread and crackles. "Works on my machine" is meaningless for audio. (2) Firefox doesn't expose underrun counts to the page. The one metric that would prove an underrun (playbackStats.underrunCount) is unavailable in the very browser that crackles — so on the affected machine, the crack can only be confirmed by ear. Much of the project's audio history is a hunt for proxies and prevention because the smoking-gun metric is missing.

The deepest one: the load-transfer stall (the real slow-machine crack)

The four tools above stop discontinuity clicks (sudden jumps). But the residual slow-machine crack on track changes turned out to be the other kind — an underrun — and its cause was the track load itself. Sending a decoded track to the worklet (addBuffers) copies the PCM across the thread boundary, and on Firefox that copy costs about 1 ms per MB — measured by instrumenting the transfer and confirming the time scales linearly with track size, not a fixed per-call overhead. A ~100 MB track is therefore a single ~120 ms blocking transfer. The audio sink only holds about 28 ms of buffered output, so a 120 ms stall on the shared audio thread (§10's catch) drains the buffer dry → underrun → crackle. On a fast machine the same event is a barely-audible "stumble"; on a slow one, a clear crack. Same event, less headroom.

The fix is to stop doing the transfer in one blocking shot. Chunked (incremental) feeding slices the track into ~3 MB pieces and feeds them to the worklet one at a time, with a short yield between each so the audio thread gets to render and refill the sink buffer between slices. The total transfer time is unchanged — it's just spread out so no single piece ever exceeds the ~28 ms the buffer can absorb. The crack disappears.

Why it's Firefox-only

Chrome renders each AudioContext on its own thread, so the load transfer never competes with playback there — Chrome's switches are already clean, and chunking would only add latency for no benefit. So the chunked path is compiled only into the Firefox build (via a build-time __BUILD_TARGET__ constant; the Chrome build dead-code-eliminates it and keeps the fast single-shot load). This is the general principle from §3 in action: treat the two browsers as separate products and fix each where it actually hurts.

The cost, and a worklet bug it surfaced

Two honest caveats. (1) Latency: spreading one ~120 ms transfer into ~35 slices-plus-yields makes the whole load take ~0.8–1 s, so a Firefox track change has a perceptible click→playback delay. That's the deliberate trade — a slightly slow switch beats a crack — and it's tunable (slice size vs. yield). (2) A latent bug: feeding one track as many slices means the worklet's input timeline now holds multiple chunks, which tripped a real bug in the time-stretch library's feeding loop (it copied past the end of a fixed buffer → RangeError: source array is too long). A one-line fix to that loop — bound the copy by the remaining destination, not a constant — makes a multi-chunk timeline safe. It's applied as a fail-loud build-time patch to the generated worklet and covered by a unit fixture, so a library upgrade can't silently drop it.

The mental model that ties it together

Treat the boundary between "no sound" and "sound" (and between one source and another) as sacred. Never cross it abruptly. Always: mute first → do the work in silence → fade in only once the engine is provably producing clean samples → on the way out, fade then drain then destroy. And — the lesson chunked feeding adds — never hand the real-time thread a single job bigger than its buffer can absorb; if a piece of work is O(bytes), break it into sub-buffer pieces and yield between them. Every constant in the table above is just a measured safety margin around those principles.

12 · BPM, waveform & predecode

A DJ tool needs to understand the music, not just play it. That analysis is CPU-heavy, so it runs in the background worker, not on the page's main thread.

BPM detection

The tempo (beats per minute) is found by an audio-analysis library (Essentia, compiled to WebAssembly) running in background/audio/analysis-worker.ts. It decodes the audio and runs beat-tracking math. The result is cached per track. A "provisional" BPM can be shown from a partial download, then corrected once the full track is analyzed.

Waveform

The waveform you scrub is not the raw 16-million-sample track — that's far too much to draw. The worker reduces it to ~300 buckets, each the peak/RMS level of a slice of the track. The UI then draws those buckets. waveform-draw.ts further groups them to fit the pixel width on screen.

War story: the stuck "Computing…" waveform

A track's waveform would finish computing but never appear — until you clicked away and back. The cause: the result was matched to the current track by an exact stream-URL string, but Bandcamp's stream URLs carry a token that refreshes. For the same track, the URL string changed between request and result, so the "is this still current?" check (which used a different, looser comparison) said "yes, show it" while the bind step (exact URL) said "no match, drop it." The computed waveform got cached but never displayed. Lesson: identity must be checked the same way everywhere. Two different "is this the same thing?" tests on the same object will eventually disagree and strand data.

Predecode (the preparation window)

To make track switches and seeks feel instant, the player predecodes a rolling window of upcoming playlist tracks into the prepared cache — bounded by the memory policy from §7. Crucially, predecoding is passive: it readies PCM but must never start playback or change ownership (rule 2 of §5). Preparing ≠ owning.

War story: reload-on-click from cache thrashing

Firefox hides the device-memory hint, so it falls back to the most conservative cache budget — about 440 MB, or only ~4 decoded tracks. On a playlist longer than that, jumping around constantly evicted tracks you'd come back to, and re-selecting one did a full network re-fetch + decode — tracks that were "prepared" kept needing to load again on click. The fix exploits a size asymmetry: decoded PCM is ~100 MB/track, but the compressed bytes are only ~5 MB/track. So the engine now retains the small encoded blobs (a whole playlist fits in a ~128 MB budget) even after evicting the big decoded buffers. A re-selected track then re-decodes locally (~300–500 ms, no network) instead of re-fetching. The expensive decoded-PCM ceiling — the thing the conservative profile exists to protect — is unchanged. Lesson: when a cache thrashes, ask whether a cheaper representation of the same thing can be kept longer than the expensive one.

13 · Coding patterns & hard-won lessons

The audio ideas are universal; these implementation patterns are how this particular codebase stays sane. They generalize to any event-heavy, async system.

Factory functions & closures, not classes

Most modules are a function that returns an object of methods, with private state captured in the closure. createHostPlayer(), createRuntimeAudioController(), etc. State is encapsulated without this-binding pitfalls.

Serialize side effects through one chain

Audio commands must not interleave (you can't "load" and "stop" the same host at once). The controller funnels them through a single promise chain — a control chain:

controlChain = controlChain.then(task).catch(logError);

Each task waits for the previous one. This turns a storm of concurrent UI events into an orderly, predictable sequence of host operations.

Transition tokens to reject stale work

When the user changes their mind mid-operation, in-flight async work must be abandoned. Each transition captures a token; when a new transition starts, the token increments. Every async step re-checks token === transitionToken before applying its result, and bails if it's stale. This is how the code survives rapid clicking without acting on outdated decisions.

Coalesce, don't queue

For high-frequency inputs (seek drags, tempo nudges), don't queue every event — keep only the latest target and act once. Queuing leads to lag and the busy-loop family of bugs.

Make state observable, then trust the debugger

The extension has a deep debug panel that prints ownership state, prepared vs. loaded vs. owned, host timings, gate values, and a transition trace. Several bugs in this guide were only solvable because the runtime state was visible. The rule the team follows: if the state you need to reason about isn't in the debugger, add it to the debugger first, before changing behavior.

The meta-lesson

Three of the nastiest bugs here — the tab-freezing busy-loop, the stuck waveform, and the eviction edge case — were not audio bugs at all. They were ordinary async/state-management bugs (no termination condition, inconsistent identity checks, boundary conditions) that happened to live in an audio system. Audio is unforgiving because it runs on a real-time deadline, so it surfaces sloppy state management loudly. Get the boring software-engineering fundamentals right and the audio gets dramatically easier.

14 · Build your own: a checklist

If you set out to build a web audio engine like this, here's the path distilled:

  1. Learn the Web Audio graph. Make an AudioContext, decode a file with decodeAudioData, play it through a GainNode, fade it in and out. Feel how currentTime scheduling works.
  2. Write a trivial AudioWorklet. Pass audio through unchanged, then apply a simple gain. Understand that it runs on the audio thread and must be fast.
  3. Add real DSP. Drop in a time-stretch library (like SignalSmith). Change tempo with pitch locked. This is the moment it feels like a DJ tool.
  4. Respect the real-time deadline. Add micro-fades on every start/stop. Never begin or end audio on a non-zero sample without a ramp.
  5. Model ownership explicitly. If more than one thing can make sound, give playback a single, named, observable owner and define exactly when it transfers.
  6. Solve gapless with double-buffering. Two engines; do the expensive load on the silent one; swap; drain the old one.
  7. Tame your inputs. Coalesce high-frequency events; serialize commands; use tokens to drop stale async work; give every retry a real stopping condition.
  8. Make it observable. Build the debug view before you need it. Audio bugs are timing bugs; you cannot fix what you cannot see — and remember some browsers hide the metric you most want.
  9. Test on a slow machine. Crackle is a CPU-budget problem; fast hardware lies to you.
